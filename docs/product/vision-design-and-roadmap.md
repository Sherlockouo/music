## 0. 文档口径

本文基于当前仓库文档、前端与播放器源码，以及运行中的桌面歌词界面整理。此次没有完成所有页面的浏览器走查，也没有重新执行完整构建、测试或第三方服务可用性验收。

因此：

- “当前能力”表示代码调用链或文档能够证明其存在，不代表所有外部服务始终可用。

## 1. 产品定位

### 1.1 一句话定位

**以网易云账号和内容为底座，为重视视觉氛围、歌词和桌面体验的用户，提供纯粹、连续、低打扰的听歌工具。**

R3PLAYX 是“网易云体验增强客户端”，不是网易云社交功能的复刻，也不是要求用户分别登录多个平台的全平台音乐聚合器。

外部能力在产品中的角色应保持清晰：

| 外部能力 | 产品角色 |
|---|---|
| 网易云 | 账号、曲库、歌单、推荐、收藏和播放元数据的主来源 |
| Unblock 等替代音源 | 官方音源不可用时的播放回退，不是另一套用户音乐库 |
| Apple Music | 高清 / 动画封面、编辑文案和艺人资料等元数据增强，不是第二个账号体系 |
| YouTube 等可选来源 | 受平台、网络和配置约束的补充音源，不作为始终可用的核心承诺 |

### 1.2 目标用户

优先服务以下用户，而不是试图覆盖所有音乐用户需求：

1. 已有或愿意使用网易云账号，希望减少社交信息干扰的人。
2. 重视封面、主题、动态背景和歌词排版的人。
3. 将桌面播放器作为日常工具，需要队列、快捷键、输出设备和系统媒体控制的人。
4. 需要在浏览器或移动设备上完成轻量浏览与播放的人。
5. 有音质、缓存、下载或离线管理需求的进阶桌面用户。

### 1.3 核心体验闭环

```text
发现音乐
  → 以可预期的方式播放
  → 管理当前队列
  → 进入歌词与沉浸体验
  → 收藏并沉淀到个人音乐库
  → 下次启动或再次访问时无缝继续
```

后续功能应优先增强这条闭环。不能改善核心闭环、平台能力或可维护性的功能，不应仅因为上游 API 已暴露就加入产品。

## 2. 产品原则与非目标

### 2.1 产品原则

| 原则 | 含义 |
|---|---|
| 音乐优先 | 内容、播放和歌词优先于社交、运营入口与装饰性配置 |
| 连续而不打扰 | 浏览、搜索、打开详情和设置时不随意打断当前播放 |
| 氛围必须服从可读性 | 封面背景和动态色可以变化，但正文、控件和焦点必须始终清晰 |
| 操作应当可预期 | 同一内容在不同页面采用一致的播放、收藏、菜单和键盘规则 |
| 自动化允许接管 | 自动跟唱、推荐、缓存和回退都应给用户明确的控制或退出方式 |
| 感知性能优先 | 先呈现稳定骨架和可用内容，再渐进加载；避免为预加载制造额外白屏与内存压力 |
| 尊重平台能力 | 桌面、浏览器和移动 Web 可以有不同能力，不制造无效开关或虚假对等 |
| 先可靠，再丰富 | 核心状态、会话、音源与缓存没有稳定前，不继续堆叠外围功能 |

### 2.2 非目标

以下事项不作为当前产品方向：

- 社交 Feed、评论社区、私信或以关系链为中心的功能。
- 完整的平台账号聚合与跨平台统一曲库。
- 在核心链路不稳定时优先加入 AI 推荐、复杂可视化或更多环境特效。
- 为追求“全新设计”而推翻已经形成的视觉识别。
- 默认将独立 Web Server 当作无需鉴权的公开多用户服务。

非目标不等于永久禁止；如果未来产品定位改变，应先更新本文，再安排实现。

## 3. 视觉与交互设计

### 3.1 必须保留的设计 DNA

#### 动态强调色

强调色不仅用于品牌按钮，还用于当前导航、播放状态、歌词进度和设置选中态。它是跨页面最稳定的状态线索。

后续应统一现有 `brand` / `accent-color` 双轨表达，并增加 `on-accent` 等前景约束，确保所有强调色上的文字和图标可读。

#### 封面环境背景

封面同时承担内容识别、背景氛围和播放器色彩来源，是产品最有辨识度的第二层视觉。

背景可以随音乐改变气质，但需要有稳定的遮罩和对比度下限。关闭背景或减少动效后，功能与信息层级不能受损。

#### 大圆角内容画布与毛玻璃

大圆角封面、内容卡片、搜索框和浮层构成柔和的内容容器；透明度与模糊优先于厚重阴影。

后续应统一 `row / card / hero / pill` 等圆角语义，避免每个页面独立扩展尺寸。

#### 沉浸式歌词

当前行放大、邻行弱化、逐词填充、自动跟随和封面背景共同形成品牌高潮。歌词页是视觉和性能结合最完整的页面，应作为后续体验增强的标杆，而不是无节制添加特效的试验场。

### 3.2 布局与排版

桌面端保留以下识别性结构：

```text
左侧主导航 + 中央独立滚动内容画布 + 右侧 Now Playing / 队列 / 播放控制
```

排版延续“工具区克制、音乐内容外放”的对比：列表和设置紧凑，详情标题与当前歌词使用更强字级。Roboto 与 Barlow 已足以支撑现有品牌，不需要为改造而增加字体。

### 3.3 动效语言

动效分为两类：

1. **反馈动效**：按压、菜单、Tabs、封面淡入淡出和页面进入，短促并可中断。
2. **环境动效**：呼吸背景、波形和歌词连续变化，服务氛围，不能阻塞操作。

工程上应明确职责：CSS 处理简单状态与持续动画，Framer Motion 处理布局 / Presence / Drawer，GSAP 处理需要时间轴的精细序列。同一基础控件不混用多套动画引擎。

`prefers-reduced-motion` 下应去掉非必要位移、回弹、视差、呼吸和自动平滑滚动，仅保留理解状态所需的透明度变化。低功耗模式和用户的减少动效偏好是两个独立开关。

### 3.4 全局交互契约

后续页面和组件统一遵循：

| 场景 | 契约 |
|---|---|
| 封面单击 | 进入对应详情，必要时预取，不直接造成意外播放 |
| 曲目激活 | 制定一套全产品统一的单击 / 双击 / 触屏规则；桌面双击不能成为唯一播放入口 |
| 键盘 | 所有主要操作可通过键盘完成，焦点清晰，Enter / Space 行为一致 |
| 更多操作 | 收藏、下一首播放、加入歌单、下载和删除等进入统一曲目菜单 |
| 搜索 | 保留 Spotlight 启动器、中文输入法处理、Esc 和焦点恢复 |
| 自动歌词跟随 | 用户滚动后暂停自动跟随，并提供回到当前行的明确方式 |
| 异步内容 | 每个内容区都有加载、空、错误、重试和必要的未登录状态 |
| 移动端 | 优先单击、明确更多按钮、底部 Drawer 和安全区；不模拟桌面双击作为唯一方式 |
| 破坏性或远程操作 | 删除、批量修改、账号切换和清理缓存需要与影响相匹配的确认及反馈 |

## 4. 信息架构与平台边界

### 4.1 当前页面分工

| 页面 | 应保持的角色 | 后续方向 |
|---|---|---|
| My | 个人音乐 dashboard | 继续播放、收藏管理和个人内容沉淀 |
| Discover | 视觉优先、低成本的随机探索 | 保留封面墙，增加换一批、方向控制和轻量解释 |
| Browse | 分类明确、可持续浏览的歌单入口 | 与 Discover 保持分工，避免变成另一面随机封面墙 |
| Album / Playlist / Artist | 内容详情与播放起点 | 统一详情头、曲目列表和动作规则 |
| Search | 快速定位与完整结果浏览 | 搜索建议、历史、按 Tab 加载及更多结果类型 |
| Lyrics | 当前音乐的沉浸空间 | 稳定同步、桌面歌词联动和可访问性 |
| Settings | 平台能力与用户偏好 | 只展示真实生效且适用于当前平台的设置 |

### 4.2 推荐的平台承诺

| 能力 | 桌面端 | 桌面浏览器 Web | 移动 Web |
|---|---|---|---|
| 浏览、搜索、收藏、在线播放 | 完整 | 完整 | 完整，但采用移动交互 |
| 队列与歌词 | 完整 | 完整 | 完整移动形态 |
| 全局快捷键、托盘、输出设备 | 支持 | 不支持 | 不支持 |
| 独立桌面歌词 | 支持 | 不支持 | 不支持 |
| 自动播放缓存管理 | 支持 | 按浏览器能力另行设计 | 不默认承诺 |
| 显式下载与文件定位 | 完整桌面体验 | 受浏览器下载与 CORS 约束 | 受浏览器约束 |
| 离线文件库 | 后续优先支持 | 不作为默认承诺 | 不作为默认承诺 |
| 系统媒体控制 | 完整平台集成 | Media Session 等浏览器能力 | Media Session 等浏览器能力 |

界面应根据当前平台隐藏或解释不可用能力，不展示“能切换但没有效果”的选项。

### 4.3 独立 Web Server 的前置决策

扩展 Web 功能前，需要明确选择：

1. **单用户自托管**：提供访问令牌、持久化卷和清晰的部署边界。
2. **公开多用户服务**：正式建设认证授权、每用户上游凭据与缓存隔离、限流、配额和滥用防护。

在这一决策完成前，不应把增加公开 Web 用户规模作为产品目标。

## 5. 当前体验的主要缺口

以下问题按对核心闭环的影响排序，不替代 backlog 中的工程细节：

| 优先级 | 缺口 | 产品影响 |
|---|---|---|
| P0 | 播放进度、音量、随机队列等状态恢复不完整 | 无法可靠延续上次听歌上下文 |
| P0 | 队列边界和音源失败生命周期不完整 | 出现错误插队、无法播放或连续跳歌等不可预期行为 |
| P0 | 移动队列缺少可靠打开闭环 | 已存在的组件不能转化为用户能力 |
| P0 | 曲目单击 / 双击规则跨页面不一致 | 用户需要猜测，触屏与键盘尤其受限 |
| P0 | 账号切换与登出的用户数据清理缺少统一边界 | 可能短暂或持续显示上一账号的数据 |
| P1 | 音质固定、缓存不区分完整维度、下载与缓存模型不清 | 无法可信地扩展无损、离线和下载管理 |
| P1 | 中间宽度布局、移动导航和窗口缩放响应不完整 | 平板、小窗口和移动路径出现功能断点 |
| P1 | 设置项存在未接线或平台不适用的开关 | 损害用户信任并增加维护成本 |
| P1 | 加载、空态、错误态和未登录引导不统一 | 异常状态容易被理解为页面损坏 |
| P1 | 焦点、ARIA、减少动效和缩放支持不足 | 键盘和辅助技术用户无法顺畅使用 |
| P2 | Discover 缺少方向控制与解释 | 有视觉吸引力，但探索效率与可重复性较弱 |
| P2 | 歌单创建、编辑、排序和批量管理不完整 | 收藏后难以进一步沉淀个人音乐库 |
| P2 | 桌面歌词与主歌词页能力有差距 | 桌面特色没有充分复用现有歌词优势 |

## 6. 分阶段产品路线

阶段编号表示依赖关系，不是日期承诺。阶段 1 完成核心验收前，不建议同时大规模推进阶段 2、3、4。

### 阶段 0：确认边界与建立基线

**目标**：让后续产品决策和工程验收使用同一套口径。

交付内容：

- 确认本文的产品定位、非目标与核心体验闭环。
- 确认桌面端为完整体验，Web 为同源 UI 下的平台适配体验。
- 对独立 Web Server 做出“单用户自托管 / 公开多用户”决策。
- 建立关键路径的桌面、移动和中间宽度走查基线。
- 将路线中的实现项拆入 backlog；已修复项从本文链接到对应记录，不在两处重复维护细节。

**完成条件**：开放决策有明确结论，核心路径有可复现的验收清单。

### 阶段 1：可信赖的播放器

**目标**：用户敢于把 R3PLAYX 作为日常主力播放器。

范围：

- 定义带版本的播放器持久化模型，恢复队列、原始队列、曲目、进度、音量、循环与随机状态。
- 统一末首“下一首播放”、删除当前歌曲、移动歌曲和歌曲不在列表等队列边界。
- 补齐音源请求取消、过期 URL 刷新、加载失败、重试上限和连续跳歌保护。
- 统一所有曲目行的鼠标、触屏与键盘激活规则。
- 修复移动队列打开、关闭和基础操作闭环。
- 建立统一未登录、加载、空、错误与重试状态。
- 建立账号登录、登出和切换时的数据清理边界。
- 清理或接通核心链路涉及的无效设置。

**暂不做**：新推荐算法、本地文件库、复杂下载管理、更多视觉特效。

**完成条件**：

- 重启恢复测试覆盖队列、曲目、进度、音量和随机状态。
- 音源失败进入定义明确的反馈和回退状态，不无声卡死、不无限跳歌。
- 各页面同一曲目操作符合统一交互契约。
- 移动队列可以打开、操作和关闭。
- 账号切换不会泄漏上一账号的 UI 数据。

### 阶段 2：可信的音质、缓存与下载

**目标**：把“能播放”升级为“音质可知、缓存可控、下载可管理”。

交付顺序：

1. **音质**：提供适用音质选项、账号权益与网络回退策略，并展示实际音质和来源。
2. **自动缓存**：统一缓存键，支持真实 Range / stream，避免重复完整下载，提供容量、有效期、占用大小和清理入口。
3. **显式下载**：提供任务列表、进度、取消、重试、真实格式、存储位置和已下载管理。
4. **桌面离线**：在以上能力稳定后支持已下载内容的离线识别与播放。

产品模型必须区分：

- **播放缓存**：自动、可过期、可清理，用户无需管理文件。
- **用户下载**：显式任务、真实格式、可定位文件、可管理历史。

**依赖**：桌面与独立服务端的音源和缓存契约必须先收敛；Web 离线需独立设计，不能直接复用桌面承诺。

**完成条件**：实际音质可验证，缓存不会串音质 / 来源 / 用户，容量策略可执行，下载任务失败可恢复，文件格式与内容一致。

### 阶段 3：一致的跨设备体验与设计系统

**目标**：保留视觉个性的同时，让后续功能复用系统能力，而不是继续复制页面。

建议沉淀：

```text
AppShell
├── PrimaryNavigation
├── GlobalTopbar
├── PageScrollContainer
│   └── PageContainer
│       ├── PageHeader / MediaDetailHeader
│       ├── SectionHeader / AsyncState
│       └── MediaGrid / TrackCollection
└── PlayerRegion
    ├── DesktopQueue / DesktopNowPlaying
    └── MobileMiniPlayer / MobileFullPlayer / MobileQueue
```

工作内容：

- 统一 `MediaCard / MediaGrid`，虚拟化只改变渲染策略，不改变外观和交互。
- 统一 `TrackRow / TrackCollection`，共享栅格、播放态、收藏、菜单和移动降级规则。
- 统一 `MediaDetailHeader`，供专辑、歌单和艺人复用。
- 建立语义化颜色、圆角、间距、层级、动效和布局令牌。
- 形成桌面 / 平板 / 移动三档 AppShell；内容网格优先根据容器宽度响应。
- 让移动端持续可达搜索、返回、设置和 Light / Dark / System 主题。
- 补齐键盘焦点、控件名称、Slider / Switch / Dialog 语义和减少动效支持。

**完成条件**：核心宽度矩阵无功能缺失；同一任务跨页面规则一致；减少动效与键盘路径通过走查；新增一个内容区块时不需要再复制一套卡片或曲目行。

### 阶段 4：发现、收藏与再听闭环

**目标**：提升内容发现后的控制感，以及收藏后的长期价值。

推荐顺序：

1. **搜索**：接入已有搜索建议，增加历史记录、按 Tab 懒加载，再评估 MV / 视频等类型。
2. **Discover**：保留封面墙，增加换一批、场景 / 风格 / 语种方向控制、轻量推荐理由和整组播放。
3. **个人音乐库**：新建、重命名、删除歌单，歌单内排序、批量添加和移除。
4. **继续收听**：恢复最近播放的列表上下文，提供继续上次歌单、最近收藏和常听艺人入口。
5. **本地内容**：仅在真实需求得到验证后，再评估本地文件扫描、本地收藏和本地歌单。

Discover 初期不需要复杂算法，优先利用现有推荐接口改善控制感、反馈和可解释性。

**完成条件**：用户能从搜索或发现进入播放，将结果沉淀到个人内容，并在之后从明确的入口继续。

### 阶段 5：强化桌面与歌词差异化

**目标**：把已有桌面能力和歌词优势做成真正难以替代的体验。

候选范围：

- 桌面歌词复用主歌词页的逐词、翻译和显示偏好。
- 桌面歌词锁定、拖拽、多显示器与位置记忆。
- 主歌词页、队列与桌面歌词之间的稳定联动。
- 按平台完善系统媒体集成；Linux 可评估 MPRIS。
- 独立低功耗与减少动效体验。

该阶段可以在核心稳定后选择低风险项穿插交付，但不能以牺牲播放器可靠性为代价。

## 7. 优先级总览

| 顺序 | 产品主题 | 代表性交付 |
|---|---|---|
| 现在 | 播放可靠性与基础路径 | 状态恢复、失败处理、队列边界、移动队列、统一歌曲激活、账号会话 |
| 下一步 | 音质与资源管理 | 音质选择、实际音质、缓存契约与管理、真实格式下载 |
| 并行基础 | 跨端一致性与设计系统 | AppShell、TrackRow、MediaGrid、语义令牌、响应式和可访问性 |
| 随后 | 内容闭环 | 搜索建议、可控 Discover、歌单管理、继续收听 |
| 最后 | 平台差异化 | 桌面歌词增强、系统媒体集成、按需离线文件库 |

阶段 2 与阶段 3 可以在阶段 1 的核心播放问题收敛后并行，但需要分别避免触碰对方正在重构的播放器边界和共享组件。

## 8. 统一验收标准

每个进入路线的特性都应回答以下问题：

1. 它改善核心体验闭环中的哪一步？
2. 支持哪些平台，不支持的平台如何表达？
3. 加载、空、错误、离线和未登录状态是什么？
4. 鼠标、触屏和键盘分别如何操作？
5. 是否影响当前播放、队列、账号数据或缓存？
6. 是否需要迁移持久化数据，旧版本如何兼容？
7. 是否涉及桌面 / server 双实现或共享 IPC 契约？
8. 是否遵守 description HTML 净化、音频路径限制和 loopback 等安全边界？
9. 是否提供减少动效、低功耗或资源清理路径？
10. 用什么自动化测试和真实界面走查证明完成？

不能因为“组件已经存在”“API 已暴露”或“设置已经能保存”就认定特性完成。

## 9. 度量与反馈

优先采用可复现验收、匿名反馈和本地诊断，不默认新增行为追踪。

建议持续观察：

- 重启后恢复核心播放上下文的成功率。
- 播放失败后的可恢复性，以及连续失败是否被安全终止。
- 各页面歌曲激活规则的一致性和关键任务完成率。
- 移动队列、搜索、返回、设置等关键入口的可达性。
- 不同窗口宽度下播放器和主要操作的完整程度。
- 音源回退、实际音质、缓存命中与清理是否符合契约。
- 下载成功率、可恢复性和文件格式正确性。
- 核心页面在加载、空态和错误态下是否仍有明确下一步。

数值目标应在获得基线后制定，不在本文凭空设定。

## 10. 待决策事项

| 决策 | 推荐默认值 | 状态 |
|---|---|---|
| 产品首要形态 | 桌面完整体验，Web 平台适配体验 | 建议，待产品负责人确认 |
| Web Server 服务模型 | 先明确单用户自托管边界，再决定是否建设多用户 | 待确认 |
| 桌面歌曲激活规则 | 保留双击快捷播放，同时提供明确单击 / 键盘入口；触屏统一单击 | 待交互走查后确认 |
| Web 离线 | 不作为默认承诺，桌面优先 | 待确认 |
| 本地文件库 | 核心闭环稳定后再验证需求 | 暂缓 |
| Discover 推荐复杂度 | 先做控制与解释，不先自研复杂算法 | 建议 |
| 用户行为度量 | 先本地验收和反馈，不默认引入新增追踪 | 待确认 |

决策确定后，应更新状态并记录日期；不要只在 Issue、聊天或代码注释中留下隐性的产品约定。
